### 0.3 现有实现（`core/flow/detail.py`）

```
DetailReader.read(fs):
    boxes1 = kit.ocr_frame(fs)        # ① 第一屏【全屏】OCR（raw 帧，不裁 ROI）
    detail = _parse(fs, boxes1)
    fs2 = _scroll_detail_page2(fs)    # 上滑一屏 + wait_state 校验
    boxes2 = kit.ocr_frame(fs2)       # ② 第二屏【全屏】OCR
    ...
_dismiss_detail_dialog(fs):
    text = _ocr_text(fs)              # ③ 弹窗判据又一次 OCR
```

**一个详情页 = 2~3 次全屏 OCR + 1 次上滑 + 若干等待**。日志实测 `详情读字段+弹窗判据 5902ms`。


**全库一把锁串行**、`ocr_dedup` 帧差去重（已有）。

## 1. 耗时拆解（详情页 7~9s 去哪了）

| 环节 | 估算 | 说明 |
|---|---|---|
| 第一屏全屏 OCR（det + rec） | ~1.5~2.0s | det 缩到 640 边（≈480×640）+ rec 约 60~100 个文本框 |
| 上滑一屏 + 稳定等待 + wait_state | ~1.2~1.8s | swipe 490~700ms + settle + 状态校验 |
| 第二屏全屏 OCR | ~1.5~2.0s | 同第一屏 |
| 弹窗判据 OCR | ~0.8~1.5s | 未复用第一屏结果时 |
| 其它（取帧、解析、写日志） | ~0.5s | |
| **合计** | **≈6~8s** | 与实测 7~9s 吻合 |

**结论**：详情页耗时 **≈70% 是 OCR**，其中"第二屏 + 弹窗重复"是主要浪费。
列表扫描 3~5s 中，大部分是滑动与等待。

| 指标 | 现状 | 目标 |

## 3. 优化方案（按性价比排序）

### 3.1 按需读第二屏 ⭐⭐⭐（已确认可行，收益最大）

用户确认：**距离和货物大多数在详情第一屏**，仅"货主要求过长"时货物才落到第二屏。

**做法**：第一屏抽完字段后判断——

```
抽取阶段（第一屏）：
    货物 = 正则「货物/货源/货品…」标签行
           若为空 → 再试「货主要求」内容里是否含货物描述（见 3.1.1）
    距离 = 距离行正则

if 距离 已拿到 and 货物 已拿到:
    跳过第二屏        ← 大多数情况走这里
else:
    才滑第二屏
```

**收益**：省 **2.5~3.5 秒/单**（一次全屏 OCR ≈1.5~2s + 上滑等待 ≈1.2~1.8s）
按"大多数命中"估算，详情页 **7~9s → 4~5s**

### 3.1.1 货物抽取增强（新增，低成本高收益）

**背景**：货主有时把货物内容写进「货主要求」，导致按"货物"标签抽不到 → 被误判为"需要第二屏"。

**做法**：双路抽取
1. 主路：「货物 / 货源 / 货品 / 货名 / 物品 / 承运」标签行（现有正则已有）
2. 辅路：**「货主要求」段落文本**，剔除"要求/备注/需/请"等套话后取实质内容

**收益**：提高第一屏货物命中率 → 直接提高"跳过第二屏"的比例，放大 3.1 的收益

### 3.2 det/rec 分离，只 rec 关键 ROI ⭐⭐⭐（效果最猛）

**做法**：
- 保留一次**全屏 det**（便宜，拿到所有文本框位置）
- **只对落在关键字段 ROI 内的文本框做 rec**（贵，rec 是大头）
- 例如：距离行、货物行、车长/车型行、价格行——rec 数量从 60~100 降到 ~8~15

**依赖**：⚠️ **必须先解决问题 1（坐标准确）**，否则 ROI 会切错行
**收益**：rec 量降 **80%+**，单次 OCR 从 ~1.5~2s → **~0.3~0.5s**

### 3.3 帧级 OCR 缓存，消除重复 ⭐⭐（用户点名要方案，已给）

**唯一入口** `ActionKit.ocr_frame(fs)` + 按 `frame_id`（或 raw 帧哈希）缓存，
读字段 / 弹窗判据 /「我知道了」判据**全部复用同一次全屏结果**。

- 禁止各模块自己调 `ocr(roi=...)`（会绕过缓存），全部收敛到 `ocr_frame()`
- 弹窗判据只需标题区文字，但既然全屏结果已缓存，直接过滤即可（零成本）

**收益**：3 次 OCR → 2 次（叠加 3.1 后 → 1 次），省 **1.5~3 秒**

### 3.4 减少"进详情"次数 ⭐⭐（杠杆受限，最大设想已排除）

**已排除**：~~列表页算单价过滤~~。列表卡片上的距离是**"距装货点"**，与运输距离不同，
不能用于 `单价 = 价格 ÷ 距离`。**结论：每个通过初审的候选都必须进详情页。**

因此本项只能做"减少无谓进入"：
- **列表页初审用其它字段粗筛**：价格 / 车长 / 车型 / 吨方（卡片上有就能先筛掉明显不合格的）
- **列表页缓存**：同一订单不重复进（`dedup` 已有，需确认生效）
- **残缺卡跳过**：首尾残缺卡不判断（已在做，可提前到列表阶段直接跳过，省一次点击 + 返回）
- **快速退出**：第一屏已能算出单价时直接判定并退出，不等第二屏（与 3.1 协同）

### 3.5 降低 `det_limit_side_len` ⭐⭐ → **列入测试计划**
640 → 480 / 320；det 耗时 ∝ 面积，可降 30~60%。字段文字较大，预计仍可读。

### 3.6 用"画面稳定"替代固定 sleep ⭐⭐ → **列入测试计划**
滑动/点击后检测帧稳定即继续，而非固定等待。每屏可省数百 ms。

### 3.7 流水线化（机械臂动作 ∥ OCR）⭐ → **列入测试计划**
现在 `OcrEngine` 全库串行锁 + 固定等待。改为：OCR 在后台线程，主线程继续下一步动作。
可隐藏大部分等待。

### 3.8 换更快模型 / 后端 ⭐ → **列入测试计划**
- PP-OCRv4 mobile det（比现用 det 快且准）
- NCNN / OpenVINO 后端
- onnxruntime 线程调优（i7-12700H 有 6P+8E，**注意 E 核可能拖后腿，建议绑 P 核或限制线程数**）

## 4. 提速估算（叠加后）

| 步骤 | 详情页耗时 |
|---|---|
| 现状 | 7~9 s |
| +3.3 消除重复 OCR | 5.5~7 s |
| +3.1 按需读第二屏（含 3.1.1 货物双路） | **3~4 s** |
| +3.2 只 rec 关键 ROI | **1.5~2.5 s** |
| +3.5/3.6 细节调优 | **~1.5~2 s** |

**结论：详情页 7~9s → 2~3s 可实现**（约 3 倍提速）。
叠加列表扫描 3~5s → 2~3s，整体每屏 **30~40s → 10~15s**。

## 6. 依赖与风险

| 项 | 说明 |
|---|---|
| **依赖问题 1** | det/rec 分离、按行 ROI、缩小扫描范围**全部以坐标准确为前提**。问题 1 未解决前，3.2 与"缩小扫描范围"无法实施（会切错行） |
