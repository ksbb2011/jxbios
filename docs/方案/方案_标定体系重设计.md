# 标定体系重设计方案（保底版本：纯摄像头 + 机械臂）

> **文档状态**：方案设计中（已与用户逐条讨论确认，待原型验证）
> **创建日期**：2026-09-09
> **适用范围**：`robot_order_picker_new`（**保底版本**）
> **重要前提**：本方案**不依赖任何投屏/截图工具**（iMouse 等）。官方一旦限制投屏，
> 系统必须能回到"纯摄像头看屏幕 + 机械臂操作"的模式继续工作，本方案即为此而设计。

---

## 0. 一句话结论

> 现在标不准的根因不是"平面无法标定"，而是：**① 镜头畸变没矫正 + ② 用仿射近似透视
> + ③ 靠死补丁补边角 + ④ 采集链路多一次横向拉伸**。
> 四件事都是**一次性可解**的。解完之后：**移动设备 = 各侧重算一次（约 1 分钟），
> 模板一次采集长期有效**。

## 1. 现状与痛点

### 1.1 当前坐标链路（5 段参数，强耦合）

```
帧像素 → screen_roi 归一化(u,v) → arm_range 线性映射 → x/y scale+offset 修正
      → top_y_adjust 顶部透视修正 → z_compensation 边角分区补偿 → 机械臂坐标
```

每一步都必须手工标定，且**顺序不可颠倒**（screen_roi → XY → z_press），任一段出错整体失效。

### 1.2 实测证据（2026-09-08 当天真实数据）

| 证据 | 数值 | 说明 |
|---|---|---|
| 四点拟合残差 | X 0.08 / Y 0.08 mm | 内部点（0.2/0.8, 0.15/0.85）很小 |
| live_click 落点偏差 | 右上 **3.1px** → 左下 **5.5px** → 右下 **9.4px** | **越靠边角越大** |
| `z_compensation` | `right:0.15 / bottom:0.15 / corner:0.3` mm | 作者早就发现边角不准，只能打补丁 |
| `screen_roi` 自动检测 | 同一场景三次给出比例 **1.60 / 1.63 / 1.67** | 受光线影响，不可靠 |
| `arm_range` 病态值 | 曾出现 `x_scale=0.76651` / `0.78541` | arm_range 失配后靠 scale 硬凑 |
| 采集链路 | `720×1280 → 960×1280`（宽 ×1.333） | 画面被横向拉伸，ROI 比例 1.595 而非 2.165 |

### 1.3 根因归纳

| # | 根因 | 后果 |
|---|---|---|
| 1 | 链路过长、5 段参数强耦合 | 改一个动全身，移动设备只能全套重标 |
| 2 | `arm_range` 由 `screen_roi` **按比例继承**（非实测） | 误差代代相传，靠 scale 硬凑 |
| 3 | 仿射（线性）无法表达透视 | 边角必然残差 → 只能靠 `z_compensation` 死补丁 |
| 4 | 补丁绑定当前设备姿态 | 设备一动补丁失效 → 又得全套重标 |
| 5 | 工具链有坑（`calibrate_xy._fit()` base/arm 空间混用） | 非 1.0 起点重跑会**抹掉**已有修正 |
| 6 | 采集链路横向拉伸 ×1.333 | 图标模板全是"横着的"，图色匹配更不准 |
| 7 | 历史包袱：`pixel_model` 字段无人消费 | 旧项目的双线性方案在重写时丢失 |

## 2. 目标

| 指标 | 现状 | 目标 |
|---|---|---|
| 落点精度 | ±4px（手工，边角 9px） | **≤3px（全屏含四角）** |
| 单次标定耗时 | 1~2 小时 | **< 2 分钟** |
| 移动设备后 | 全套重标 | **视觉侧/执行侧各重算 1 分钟** |
| 模板 | 跟着失效、需重采 | **一次采集长期有效** |
| 人工介入 | 需点笔尖、判断、反复试 | **全自动，只需点一次"开始"** |

## 3. 核心设计：引入"手机屏幕坐标系"做中间层

### 3.1 现在 vs 目标

```
【现在】摄像头像素 ──（5 段参数，一步跳）──> 机械臂坐标
                     ↑ 耦合、脆弱、补丁多

【目标】摄像头像素 ──①──> 手机屏幕坐标 ──②──> 机械臂坐标
                         （稳定中间层）
```

**为什么关键**：手机屏幕坐标（如 iPhone X 的 375×812 点）是**设备固有**的，
不随摄像头位置、光线、支架姿态变化。把它作为中间层后：

- 摄像头歪了/远了/换了 → **只重算①**
- 机械臂/支架挪了 → **只重算②**
- 模板记的是"屏幕第几行第几列" → **永远有效**

### 3.2 ① 视觉侧：摄像头画面 ↔ 手机屏幕坐标

- 手机全屏显示**已知位置的图案**（ArUco 网格 / 点阵，铺到四角）
- 摄像头拍一帧，识别图案角点
- 已知"图案在屏幕第几行第几列" + "图案在画面第几个像素" → 求对应关系
- 若先做一次镜头内参标定（棋盘格），可**同时消除镜头畸变**
- 点足够密（几十上百个）时，连"越靠边越鼓"的径向变形也能一起拟合掉

### 3.3 ② 执行侧：手机屏幕坐标 ↔ 机械臂坐标

- 机械臂去点图案上的**已知靶点**
- 手机端通过**触摸事件**把"真实触点坐标"回传电脑
- 直接得到 `目标点 → 实际触点` 的误差，**无需摄像头量笔尖**
- 拟合双线性模型（含 u×v 交叉项）→ 写入配置

> 这一步的精度取决于手机上报的触摸坐标（误差 <1 点），
> 远优于现在"摄像头拍笔尖 + 帧差法猜落点"的方式。

### 3.4 为什么这样能根治

| 痛点 | 解法 |
|---|---|
| 边角不准 | 图案铺到四角 + 拟合透视/径向变形，`z_compensation` 可删 |
| 移动设备要全套重标 | 两步解耦，各侧重算 1 分钟 |
| 模板失效 | 模板迁到屏幕坐标系，与相机无关 |
| 工具链 bug | 不再依赖 `scale/offset` 那套，直接拟合最终模型 |
| 光线影响 | ArUco 角点对光照鲁棒（不像现在的亮度阈值自动检测） |

## 4. 载体：手机端"标定界面"

### 4.1 页面内容设计

一个全屏界面，同时提供四种能力：

```
┌─────────────────────────────┐
│ 状态栏：连接状态 / 当前靶点  │
├─────────────────────────────┤
│                             │
│   ArUco / 点阵网格（铺满）   │  ← 视觉侧标定用（摄像头看）
│        + 靶心圆圈            │  ← 执行侧标定用（机械臂点）
│                             │
│   [可切换] 图标测试区         │  ← 模板识别率测试用
│   [可切换] 纯色 / 网格        │  ← 采模板背景用
└─────────────────────────────┘
   触摸事件 → 实时上报触点坐标到电脑
```

### 4.2 三种实现路径

| | **方案 A：网页 standalone** | **方案 B：原生壳 + WKWebView**（推荐） | **方案 C：纯原生 App**（备选） |
|---|---|---|---|
| 做法 | Safari 打开 → "添加到主屏幕" | Swift 壳（~30 行）内嵌 WKWebView 加载 HTML | 全部用 SwiftUI/UIKit 画 |
| 真全屏 | ✅（standalone 模式） | ✅ | ✅ |
| 坐标稳定 | ✅ | ✅ | ✅ |
| **屏幕常亮** | ❌ 无法保证 | ✅ `isIdleTimerDisabled` | ✅ |
| 后台驻留 | ⚠️ Safari 可能被挂起 | ✅ | ✅ |
| 离线能力 | ❌ 需 Wi-Fi 访问电脑 | 🟡 页面可内置（仍需网回传坐标） | ✅ 可完全离线 |
| 开发成本 | **最低（0）** | 低（Swift 30 行 + HTML） | 高（全部重写） |
| 内容热更新 | ✅ 改 PC 上的 HTML 即可 | ✅ 开发期走 URL，生产期内置 | ❌ 改一次编一次 |
| 代码复用 | 与 B 共用 99% HTML/JS | 与 A 共用 99% | 独立 |

**推荐路径**：**先 A 验证算法 → 再 B 上生产**；若 B 有硬伤（极少见）再走 C。

### 4.3 ⚠️ 铁律：可视区域必须一致

> **校准时的可视区域，必须 == 运满满运行时的可视区域。**

旧方案失败的第一主因就是违反这条：Safari 有地址栏且工具栏会**自动收放**，
`window.innerHeight` 一直在变，而运满满是真全屏——学到的坐标系天生就是歪的。

- 方案 A：必须"添加到主屏幕"以 standalone 打开（普通 Safari 标签页不行）
- 方案 B/C：原生全屏天然满足
- 校准前需确认：**无状态栏遮挡 / 无刘海安全区偏移 / 无底部横条**

## 5. 完整标定流程（目标 < 2 分钟）

### 阶段一：视觉侧（①）

1. 手机打开标定界面，显示 ArUco 网格，全屏、常亮
2. 摄像头抓 1 帧（多帧取平均抗抖动）
3. 识别角点 → 与已知屏幕坐标配对 → 求对应关系（含畸变项）
4. 自检：重投影误差应 < 1px，四角误差应 < 2px

### 阶段二：执行侧（②）

1. **先单独测一次 Z 深度**（不再每点扫，旧方案这里浪费了大量时间）
   - 从浅到深试压，手机一上报触点即停 → 得到 `z_press`
2. 机械臂依次点 **16 个网格点 + 8 个随机点**
3. 手机每收到一个触摸，立即上报 → 电脑记录「目标屏幕坐标 ↔ 实际触点坐标」
4. 拟合双线性模型（含 u×v 交叉项）
5. **第 3 轮验收**：再点 10 个点，只测不纠偏，报告最大误差

### 阶段三：验收与写入

- 精度达标（≤3px）→ 写入配置
- 不达标 → **报警并提示原因**（不硬写），常见原因：
  - 机械臂有机械间隙/回差 → 建议单向趋近
  - 屏幕未真正全屏 → 检查可视区域
  - 某个区域系统性偏 → 摄像头角度或支架松动

### 写入的配置（建议格式）

```jsonc
"calibration": {
  "vision": {                    // ① 视觉侧
    "model": "homography",       // 或 homography+radial
    "H": [ ... 9 个系数 ... ],
    "distortion": [k1, k2, p1, p2],   // 可选
    "screen_size": [375, 812],   // 手机屏幕逻辑分辨率
    "calibrated_at": "2026-09-09T10:00:00",
    "reproject_error_px": 0.6
  },
  "actuation": {                 // ② 执行侧
    "model": "bilinear",
    "ax": [ ... 4 系数 ... ],     // ax = f(u,v) = c0 + c1*u + c2*v + c3*u*v
    "ay": [ ... 4 系数 ... ],
    "max_error_pt": 2.4,
    "z_press": 6.3
  }
}
```

> 迁移期保留 `screen_roi / arm_range / x_scale...` 作为**回退路径**，
> 新模型不可用时自动降级到现有逻辑，保证生产不中断。

## 6. 拓展能力（同一载体，几乎零额外成本）

标定界面建好后，下面这些能力可以逐步长出来：

### 6.1 图标模板自动采集 ⭐
- 界面上按**已知坐标**渲染业务图标（返回箭头、分享、抢单按钮…）
- 一键：抓帧 → 按已知坐标裁切 → 自动命名入库 → 更新 `templates.json` + ROI
- **收益**：告别手动截图裁剪；ROI 天然正确（因为是算出来的，不是框出来的）

### 6.2 识别成功率批量测试（体检报告）⭐⭐
- 界面渲染一批图标 + 干扰元素
- 在不同光线/角度/亮度下各跑 N 次
- 输出报表：每个模板的 `命中率 / 平均分 / 分数分布 / 卡线风险`
- **收益**：用数据定阈值（留 ≥0.04 余量），不再拍脑袋；能提前发现"卡线模板"

### 6.3 点击精度批量测试 ⭐⭐
- 随机点 100 个已知坐标 → 手机上报实际触点
- 输出：`平均误差 / 最大误差 / 误差热力图（哪个区域最差）`
- **收益**：一眼看出是整体偏移还是某个角有问题；标定后可当场验收

### 6.4 运行时漂移自检与自动修复 ⭐⭐⭐
- 每次启动 / 每 N 屏，用屏幕边缘或图案复检一次视觉侧
- 偏差 < 阈值 → 自动微调；超阈值 → 暂停并报警
- **收益**：设备被碰一下不用人工介入，"移动即崩溃"彻底解决

### 6.5 模板 ROI 全量迁移到屏幕坐标
- 所有模板的 `roi` 从"相机像素归一化"改为"手机屏幕归一化"
- 匹配时：先把当前帧通过 ① 变换到屏幕坐标系再匹配（或把 ROI 反变换到帧坐标）
- **收益**：摄像头怎么动都不用重采模板

### 6.6 Z 深度一次性标定 + 分区域记录
- 不再每点扫描（旧方案最慢的地方）
- 可选：记录不同区域（中心/四角）的 `z_press`，应对屏幕不平整

### 6.7 机械臂回差（间隙）补偿
- 每个靶点分别用"从左上趋近"和"从右下趋近"两种方式点击
- 差值即回差 → 统一改为**单向趋近**或做补偿
- **收益**：消除机械间隙导致的系统性偏差

| 阶段 | 内容 | 成本 | 产出 / 目的 |
|---|---|---|---|
| **P0** | PC 端：图案生成 + HTTP 服务 + 触点采集 + 拟合 + 写配置 | 中 | 核心算法（与手机端形态无关） |

## 9. 与旧项目 `calibrate_web.py` 的关系

旧项目 **已经实现过**本方案的"执行侧"原型（`tools/calibrate_web.py` +
`server/calib_server.py` + `tools/calibrate_btn.py`），思路是对的，但存在以下问题：

| # | 旧方案问题 | 本次修正 |
|---|---|---|
| 1 | **iPhone Safari 无法真全屏**（`requestFullscreen` 仅 iPad 支持），可视区域与运满满不一致 | 用 standalone / 原生壳，保证可视区域一致 |
| 2 | 命中容差过松（6% 屏宽 ≈ **22px**），比手工标定还差 | 收紧到 **≤3px**，并加"只验收不纠偏"的第三轮 |
| 3 | **只解决执行侧**，视觉侧（screen_roi、模板）完全没管 | 同一界面同时解决两侧 |
| 4 | 太慢：60 点 × 每点 Z 扫描（12 档 × 2.5s） | Z 只测一次；点数 16+8；事件驱动不等固定时长 |
| 5 | 重写时丢失（`pixel_model` 成孤儿字段，`core/` 零引用） | 新模型作为一等公民，保留旧字段做回退 |

**移植价值**：HTTP 服务 + 触摸上报 + 双线性拟合的骨架可直接复用，不需要从零写。

## 10. 风险与待确认

| 风险 | 说明 | 应对 |
|---|---|---|
| 摄像头分辨率不足 | 屏幕在快帧中仅约 321×512 px，ArUco 太小可能识别不稳 | 用大尺寸、低密度字典（如 4×4）；必要时用全分辨率帧做标定（标定不必用快帧） |
| 屏幕反光 | 亮屏 + 图案可能被反光淹没 | 降低屏幕亮度/加遮光罩；ArUco 对均匀反光鲁棒 |
