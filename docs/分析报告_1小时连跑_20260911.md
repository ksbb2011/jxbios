### 2.2 详情页停留时间（约 17 秒）—— 重点

实测一个完整详情页时序：

```
19:54:03 点击进详情
19:54:14 检测到 detail 状态   ← 间隔 11 秒（最大头！）
19:54:17 详情读字段 2688ms
19:54:17 判定合格，停留 2.5s
19:54:21 点击返回箭头
19:54:22 回到列表
```

**详情页总停留 ≈ 17 秒，构成：**

| 步骤 | 耗时 | 占比 |
|---|---|---|
| ① 点击进详情 → 检测到 detail 状态 | **~11s** | 65% ⚠️ |
| ② 详情读字段+弹窗判据 | 2.7s | 16% |
| ③ 判定后停留 hold | 2.5s | 15% |
| ④ 点返回 → 回到列表 | 1s | 6% |

**结论**：详情页停留久的主因不是"读字段"（只有 2.7s），而是 **① 点击进详情后，要 11 秒才检测到"已进入详情页"状态**。

这 11 秒 = 机械臂点击 + `wait_state(4s)` 等待 + 主循环逐帧 `detect`（每帧匹配多个模板约 1~2s）。详情页加载（App 网络请求）+ 每帧 detect 慢，叠加导致要 11 秒才确认"已经到详情页了"。

## 四、你的 6 个问题逐一回答

### 问题 1：详情页停留时间久？

**是"进详情后检测状态"慢，不是"读字段"慢。** 详情页总停留约 17s，其中：
- 读字段只有 2.7s（你担心的"检测"其实很快）
- **大头是"点击进详情 → 检测到 detail 状态"花了 11s**（detect 每帧匹配多个模板慢 + 详情页加载）

### 问题 2：返回列表后为何有间隔才点下一个？是否重新检测了？

**是，返回列表后重新整屏 OCR 了。** 当前逻辑是"无状态"的：

```
每屏 scan_once（整屏 OCR 2s + 切卡判定）→ 命中列表（有坐标）
→ 只点第 1 张进详情 → 返回列表
→ 主循环下一轮又 scan_once（重新整屏 OCR 2s）→ 再点下一张
```

你的想法完全对：**一屏有 3 个命中，坐标是现成的，本应缓存命中列表，详情返回后直接点第 2、3 个坐标**，而不是重新 OCR。当前实现**没有缓存命中坐标**，每屏命中列表用完即丢。

**原因**：主循环设计原则是"每轮重新取帧判定，绝不跨帧复用"（防列表因 App 自动刷新而变化）。但代价是详情返回后多花 2s 重新 OCR。

### 问题 3：详情页左下角没金额，页面里金额能检测到吗？

**能。** 双重保障：
1. 主路径：全屏"数字+元"取最大（金额无论在左下角还是页面中间都能取到）
2. 兜底：详情页读不到价格 → **回退用列表卡片价格**（本小时触发 2 次，均回退成功 950 元）

### 问题 4：是否遇到"推荐货源/没有更多"？是否自动换路线？

**都遇到了，且自动换路线了。**

```

20:10:43 检测到「推荐货源 该线路无更多符合条件货源，为您推荐」→ 触发换路线
20:11:03 开始设置 B 路线
```

流程：A 路线扫到底 → 识别"推荐货源/无更多"→ 自动切 B 路线 → 重设城市 → 继续扫，直到 1 小时定时收工。**换路线 + 无订单检测都正常。**

### 问题 5 & 6：完整流程梳理 + 多维度分析

**完整流程**（每个循环）：
```
取帧 → detect 页面状态 → 分发处理
  ├─ 列表页：整屏 OCR(2s) → 切卡 → 逐卡判定(车长/车型/载重/排除词) → 命中列表
  ├─ 点命中卡进详情：点击 → 等 detail 状态(11s) → 读字段(2.7s) → 判定 → 停留2.5s → 返回

  └─ 本屏点完/到底：上滑一屏 / 到底换路线
```

## 五、发现的问题与优化建议（按收益排序）

### 🔴 高收益（显著提速）

1. **缓存命中坐标，避免详情返回后重新 OCR**（对应你的问题 2）
   - 现状：详情返回列表后重新整屏 OCR（2s）才点下一个
   - 优化：scan_once 的命中列表（含坐标）缓存起来，详情返回后**直接点缓存的下一个**，本屏点完才重新 OCR
   - 预期：每单省 2s，108 单省约 3.6 分钟
   - 风险：列表可能因 App 刷新而变化，需加"返回后快速比对列表是否变化"的检测

2. **降低"进详情→检测到 detail"的 11s**（对应你的问题 1）
   - 主因：detect 每帧匹配多个模板慢 + 详情页加载
   - 优化方向：a) 点击进详情后，先用"详情页返回箭头模板"快速确认（单一模板，比全量 detect 快）；b) 缩短 wait_state 超时；c) 详情页加载期间跳过全量 detect

### 🟡 中收益

3. **详情读字段的 16 次超 5s**：核心字段缺失才滑第 2 屏，但第 2 屏 OCR 又 2s。可优化为"第 1 屏字段够了就直接判，第 2 屏只在价格/距离缺失时才滑"（当前已是这个逻辑，16 次是确实缺字段，属正常）

### 🟢 低收益 / 观察项

4. **方数大量 None**：方数 OCR 常漏读，但不影响判定（拼单才用）。若将来拼单多，需收窄方数 ROI。
5. **detect 慢**：每帧匹配多模板约 1-2s，是全局速度瓶颈之一。可评估减少每帧匹配的模板数（按当前状态只匹配相关的几个）。
